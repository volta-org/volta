## Описание проблемы

**Проблема:**

Современные архитектуры требуют регулярного нагрузочного тестирования. Существующие решения имеют высокий порог входа:
- Сложная настройка кластера генераторов нагрузки
- Анализ результатов требует ручного труда (поиск в логах)
- Отсутствие единого центра управления тестами в командах (риски безопасности)

**Текущие альтернативы:**
- **JMeter:**  Не сложен в освоении, стандарт индустрии, но потребляет много ресурсов (Thread-per-user model), сложен в CI/CD, старый UI
- **Gatling/K6:** Хороши для разработчиков, но требуют написания кода, слабая визуализация в бесплатной версии.
- **BlazeMeter:** данные уходят в облако (проблема безопасности для банков)

## Целевая аудитория

**Потребности и ожидания:**
- **QA:** Хочет запустить тест на 50k RPS одной кнопкой, без настройки серверов.
- **Dev:** Хочет сразу увидеть причину падения, не ища проблему в логах
- **SRE:** Хочет гарантий, что тесты не уронят Prod

## Стейкхолдеры

**Ключевые стейкхолдеры:**
1. **Корпоративные клиенты:** CTO или IT-директора банков/финтеха, которые принимают решение о закупке лицензии.
2. **Open Source Community:** Пользователи бесплатной версии, которые тестируют ядро, заводят баги и популяризируют продукт.
3. **Служба безопасности клиента:** Те кто следят за ПО в банке: разрешают (или запрещают) установку
4. **Команда разработки:** Внутренняя команда, определяющая вектор развития и приоритеты.
5. **Инвесторы / Основатели:** Лица, финансирующие инфраструктуру на этапе стартапа.

**Роль стейкхолдеров и их влияние:**
- **Корпоративные клиенты:** Обеспечивают монетизацию. Их требование — SLA и поддержка. Влияют на приоритет Enterprise-фич (SSO, отчеты).
- **Open Source Community:** Обеспечивают обратную связь и бесплатное тестирование. Влияют на качество ядра и репутацию бренда.
- **Служба безопасности:** Имеют право на запрет фич. Влияют на архитектуру (требование On-Premise).
- **Команда разработки:** Балансирует между хотелками клиентов и техническим долгом. Принимают решения "Что делаем сейчас, а что потом".

## Бизнес-цели и ключевые метрики

**Основные бизнес-цели:**
1. **Сокращение времени анализа инцидентов:** Снизить время "обнаружение ошибки → решение" при анализе результатов с 4 часов до 15 минут за счет AI-аналитики  после внедрения AI анализатора
2. **Экономия инфраструктуры:** Снизить потребление ресурсов на генерацию нагрузки на 40% (по сравнению с JMeter) за счет использования Virtual Threads к релизу v1.0.
3. **Монетизация:** Привлечь 10 корпоративных клиентов на платную подписку в течение 6 месяцев после релиза

**KPIs:**
- **Time to Analyze:** Среднее время от завершения теста до получения отчета с причинами сбоя.
- **Adoptation %:** % команд внутри компании, перешедших на Volta с JMeter.

## Описание продукта

**Общая концепция:**
Volta - это решение для автоматизации нагрузочного тестирования HTTP сервисов. Система решает проблему сложности настройки кластера генераторов нагрузки и ручного анализа причин сбоев.

**Ключевые функции (USP):**
1. **UDP-Discovery:** Автоматическое обнаружение агентов
2. **AI анализ:** модель, обученная на паттернах отказов JVM, автоматически подсвечивает аномалии в коде.
3. **Права доступа:** Единый портал с историей запусков, правами доступа и очередью задач.

## Риски

**Риски и стратегии:**
1. **Технический риск:** Технология новая, возможны баги в JVM
    - *Стратегия:* Тщательное тестирование на LTS версиях Java, фоллбэк на классические потоки при необходимости
2. **Рыночный риск:** K6 активно растет
    - *Стратегия:* Фокус на фиче "AI анализатор" и "Безопасность данных" (нет у K6 Cloud)
3. **Риск внедрения:** JMeter - стандарт
    - *Стратегия:* Разработка конвертера скриптов JMeter (JMX) → Volta.

## Основные функции продукта (Scope)

**Входит в MVP:**
- **Core:** Генерация HTTP/2 нагрузки (GET, POST)
- **Multicast:** Подключение 1 агента в кластер (Master-Agent)
- **UI**: Отсутсвует (статистика выходит в файл)
- **AI:** Отсутствует.
- **Enterprise:** Базовая ролевая модель (Admin/User).

**Не входит в MVP:**
- Поддержка протоколов gRPC, WebSocket
- Интеграция с CI/CD

## Версии продукта и план развития

**MVP:**
- Стабильный движок нагрузки..
- Отчеты в CSV

**v1.1:**
- Интеграция с локальной LLM для анализа
- Рекомендации по тюнингу JVM

**v2.0:**
- Плагины для CI/CD
- Поддержка gRPC и Kafka

## Ограничения

**Бюджет:**
- Разработка ведется силами внутренней команды (Pet-project mode → Startup).
- Инфраструктура: $200/мес на облачные серверы для демо-стенда

**Сроки:**
- Прототип: 1 месяц.
- MVP: 3-4 месяца.
- Релиз v1.0: 6 месяцев.

**Ресурсы:**
- Команда: 1 Backend (Java), 1 Frontend (Thymeleaf + Chart.js), 1 QA/Analyst.
- Стек: Java 21, Spring Boot, PostgreSQL (TimescaleDB)
